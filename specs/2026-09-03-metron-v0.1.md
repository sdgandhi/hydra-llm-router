# Metron v0.1

## Summary

Metron is Hydra's local observability and reporting subsystem for Codex. It is enabled by default, runs inside the existing Hydra process, stores privacy-safe operational telemetry on the user's machine, and serves a local dashboard. The primary unit is a Codex user turn.

Benchmarking is intentionally separate from the packaged Hydra application. The repository contains a standalone configurable benchmark module, versioned benchmark configurations, and dated run artifacts, but the macOS application bundle excludes all benchmark code and data.

## Product behavior

- Observe Hydra-routed Responses traffic exactly and arbitrary Codex Desktop activity on a best-effort, near-real-time basis.
- Record latency, time to first output, model and route, retries and fallback, token usage, tool counts and statuses, approvals when observable, failures, and explicit user interventions.
- Never turn unavailable measurements into zero. Every value carries `exact`, `reconciled`, `estimated`, or `unknown` completeness.
- Store no prompt text, response text, command text, paths, diffs, tool arguments, or tool output in normal Metron telemetry.
- Keep all telemetry local. Metron has no upload or hosted-service path.
- Estimate OpenAI cost as a dated API-list-price equivalent, clearly distinguished from actual ChatGPT billing.
- Estimate local inference cost from generation duration and a configurable machine-hour rate. The default is `$0` per machine-hour.

## Runtime architecture

Metron starts with Hydra unless `[metron].enabled = false` is configured.

### Sources

1. **Hydra Responses instrumentation** emits exact model-call lifecycle records: requested model, selected route, concrete target, retry/fallback, start, first output, completion/failure/cancellation, duration, and usage.
2. **Codex session ingestion** tails persisted session JSONL beneath the configured Codex home. It captures new records from arbitrary Desktop sessions, resumes safely after restarts, ignores partial lines, and reconciles completed turns. Persisted formats are versioned by Codex CLI version and parsed through compatibility adapters.
3. **App-server ingestion** is available to external runners such as the benchmark module. It accepts the documented thread, turn, item, approval, and token events without making the packaged app responsible for launching benchmark sessions.

The app-server protocol exposes streamed turn/item events, approval requests, tool completion state, durations, failures, and thread token updates: <https://developers.openai.com/codex/app-server>.

### Event store

Canonical records are append-only JSONL partitions at `~/.hydra/metron/events/YYYY-MM-DD.jsonl`. Mutable ingestion cursors live at `~/.hydra/metron/cursors.json` and are never required to rebuild reports.

Every canonical record uses this envelope:

```json
{
  "schema_version": 1,
  "event_id": "...",
  "source": "hydra|codex|app_server|evaluator",
  "type": "...",
  "occurred_at": "ISO-8601",
  "observed_at": "ISO-8601",
  "session_id": "...",
  "turn_id": "...",
  "generation_id": "...",
  "completeness": "exact|reconciled|estimated|unknown",
  "data": {}
}
```

Identifiers may be retained locally for correlation. Exports replace them with stable bundle-local pseudonyms. Project filters use a project basename or pseudonym, never an absolute path.

### Turn metrics

- Turn duration runs from the observed task start to completed, failed, interrupted, or aborted state.
- Time to first output is exact when provided by Hydra or Codex and otherwise unknown.
- Tool activity is stored as identity, status, duration, exit status, approval state, and byte/count metadata only.
- Explicit interventions include approval decisions, denials, request-user-input answers, steering, and manually labelled corrective follow-ups. Metron does not infer corrective intent from an ordinary later prompt.
- Operational completion and evaluated outcome are separate fields.
- Cost per successful task is calculated only for turns with an evaluator-supplied success result.

### Configuration

```toml
[metron]
enabled = true
capture_codex = true
machine_hour_usd = 0
rate_card = "bundled"
```

Unknown keys fail validation. An unavailable rate card or usage measurement produces an unknown estimate rather than an error or zero.

## Dashboard and CLI

Hydra serves the dashboard from its existing loopback listener at `/metron/` and read-only JSON endpoints under `/metron/api/v1/`. Requests with a non-loopback host are rejected.

Dashboard views:

- **Overview:** turn count, operational completion, evaluated success, cost per successful task, P50/P95 duration, first-output latency, tokens, tools, failures, and interventions.
- **Turns:** filterable privacy-safe turn list and lifecycle detail.
- **Benchmarks:** summaries and artifacts from committed benchmark run directories when present; this view is hidden or empty when no runs are available.

CLI surface:

```text
hydra metron status
hydra metron dashboard
hydra metron import --since <ISO-date>
hydra metron export --from <ISO-date> --to <ISO-date> --format jsonl|csv|html
```

The Hydra menu bar displays Metron status and provides an **Open Metron Dashboard** action.

## Separate benchmark module

Benchmark code lives under `benchmark/` and is excluded from the application bundle. It runs from the repository with its own package scripts and imports only stable Metron schemas/utilities intended for offline use.

Each benchmark is driven by a committed JSON configuration. Configuration selects routes, tasks, repetitions, timeouts, concurrency, evaluator settings, rate cards, fixture commits, and the output directory. No route or model is hard-coded in the runner.

The initial committed configuration compares:

- `lmstudio/google/gemma-4-26b-a4b-qat`
- `gpt-5.6-sol`
- `hydra/money-saver`

The task corpus contains 50 version-pinned public-fixture tasks: ten each for simple coding, repository navigation, editing, tool use, and ambiguous reasoning. Tasks run serially in clean isolated copies with network disabled and bounded runtimes. One complete round runs every task-route pair once. Later rounds are separate user-triggered runs.

Evaluation is hybrid and route-blinded:

- deterministic checks for exact output, tests, repository state, and tool outcomes;
- structured rubric scoring for tasks where judgment is irreducible;
- task-specific pass criteria;
- explicit evaluator model, prompt hash, method, score, success, evidence, and optional manual override.

Normal Metron telemetry remains metrics-only. Benchmark runs explicitly opt into retaining the prompts, outputs, checks, normalized events, and scores needed to inspect that run.

Each invocation writes a dated, versioned, append-only directory such as:

```text
benchmark/runs/2026-09-03-v1/
  config.json
  environment.json
  events.jsonl
  results.jsonl
  summary.json
```

Run directories are committed to the repository. The dashboard may serve their summaries and files when they exist, but Hydra's application package must not include them.

## Verification

- Unit-test event validation, partial records, file rotation, cursor recovery, deduplication, redaction, correlation, cost math, percentile math, and unknown handling.
- Test direct, synthetic, retry, fallback, streaming, cancellation, and failure telemetry without using the Desktop listener.
- Verify default telemetry and exports contain none of the prohibited content fields.
- Test dashboard filters, empty benchmark states, malformed data, and loopback host validation.
- Test benchmark configuration validation, fixture isolation, route blinding, evaluator schemas, timeouts, and dated run-directory creation.
- Run `npm run test:check`, build a development DMG, and run isolated end-to-end telemetry and benchmark smoke tests.
- Run one configured benchmark round and commit its dated artifacts. Do not optimize the routing policy or run additional rounds unless separately requested.

## Delivery

Work directly in the Hydra repository. Commit small verified vertical slices to `main` and push after each slice. Do not create a separate Metron repository.
